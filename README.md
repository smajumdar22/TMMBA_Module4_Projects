# Vibe Matcher

A command-line song recommender that takes a mood, genre, or reference artist
and returns real, verified songs — never fabricated ones.

```bash
python vibe_matcher.py "moody indie rock like Phoebe Bridgers, no sad songs"
```

## What it does

You describe what you want in plain text — a mood, a genre, a reference
artist, an activity ("upbeat songs for a run") — plus optional exclusions
("no sad songs", "clean only", "nothing explicit"). Vibe Matcher returns
8–10 real songs, each with the artist, title, and a one-line reason it
matches your request (naming the specific mood/genre tag that justified
the pick, so you can sanity-check the logic yourself).

Every song it can possibly return lives in [`songs.json`](songs.json), a
local dataset of ~177 real, well-known songs I curated from my own
knowledge (not generated by the AI layer), each tagged with genre(s), mood
tags, and an explicit flag. The AI's only job is to judge which of those
177 songs fit your request — it is never allowed to introduce a song that
isn't already in the file.

## Architecture: a 70/30 split

The whole point of this project is that the "AI part" is small, and
everything around it is boring, deterministic, testable Python:

- **The boring 70%** (no AI call, plain logic) — parsing your request for
  exclusion constraints, loading and vocabulary-building the dataset,
  flagging vague/contradictory requests, **validating** every AI-suggested
  song against the dataset, re-checking exclusions against ground truth,
  deduping, and formatting output. In `vibe_matcher.py`, every function in
  this category is labeled `BORING 70%` in a section comment.
- **The AI 30%** — exactly **one** Claude API call per request
  (`get_ai_candidates`), which is handed the full dataset and your cleaned
  request, and asked to pick and rank candidates with reasons. It does not
  see the internet, doesn't generate new songs, and its output is treated
  as **untrusted** the moment it comes back.

## The accuracy layer (this is the part that matters)

The AI is a judge, not a source of truth. Every response goes through a
validator before anything reaches you:

1. **Existence check.** Every candidate is matched against `songs.json` by
   exact (case/whitespace-normalized) artist + title. Anything that
   doesn't exist in the dataset is silently dropped — the AI cannot
   introduce a song that isn't already verified real, because it can only
   "pick" from a closed list, and even a hallucinated pick gets caught
   here.
2. **Constraint re-check.** If you excluded something ("no sad songs",
   "clean only"), the validator re-checks every *surviving* song against
   the dataset's own tags — not against what the AI claims. The AI is told
   about your exclusions as a courtesy (it usually honors them), but the
   validator doesn't trust that; it enforces them independently.
3. **No padding.** If fewer than 5 songs survive validation, the tool
   doesn't pad the list with weaker matches — it tells you "I could only
   confidently match N songs" and shows exactly what it has, plus a
   breakdown of why the rest were dropped (not in dataset, excluded mood,
   excluded genre, explicit, duplicate).
4. **Low-confidence signaling.** Before the AI is even called, a heuristic
   checks whether the request is too vague (no recognizable mood, genre,
   artist, or activity signal — e.g. just "music") or self-contradictory
   (e.g. asking for both "sad" and "upbeat" without negating either). If
   so, the tool says so explicitly instead of quietly forcing out 10
   results that don't really fit.
5. **Shown reasoning.** Every surviving song displays the AI's one-line
   reason plus its actual mood/genre tags from the dataset, so you can
   check the logic yourself rather than trusting a black box.

### Failure modes considered

| Failure mode | How it's handled |
|---|---|
| AI fabricates a song or artist/title pairing | Existence check against `songs.json` by exact match — anything not found is silently dropped, never shown. |
| AI ignores an exclusion ("no sad songs" but returns a sad song anyway) | The validator re-checks every survivor's real tags from the dataset, independent of what the AI said or did. |
| Vague request ("just play something") | Heuristic detects no mood/genre/artist/activity signal in the cleaned query and flags low confidence before returning results. |
| Contradictory request ("sad but upbeat") | Heuristic checks a table of opposite mood pairs against words actually present in the request (skipping cases where one side is itself excluded) and flags it. |
| Too few good matches exist in the dataset | If fewer than 5 songs survive validation, the tool refuses to pad the list and says exactly how many it could confidently match. |
| Duplicate picks from the AI | Deduped by normalized (artist, title) before display. |

### Accuracy vs. coverage trade-off

This is the central trade-off of the whole design: because every result
must exist in a small, hand-curated dataset, **every song you get back is
guaranteed real** — there's no risk of a smooth-sounding but fabricated
"Artist X — Song Y" slipping through, which is the main failure mode of
letting an LLM freely generate music recommendations. The cost is
**coverage**: with ~177 songs, the dataset can't represent every artist,
subgenre, or era, so a sufficiently niche or obscure request (a specific
deep cut, a very narrow subgenre, an artist not in the file) will come
back with few or no matches — and the tool is designed to say so plainly
rather than stretch the dataset to cover a gap it can't. Growing the
dataset (more songs, broader genre coverage) is the intended way to widen
coverage without weakening the accuracy guarantee, since the same
validator applies no matter how large `songs.json` gets.

## Setup

```bash
pip install -r requirements.txt
cp .env.example .env
# edit .env and add your ANTHROPIC_API_KEY
```

## Usage

### CLI

```bash
python vibe_matcher.py "moody indie rock like Phoebe Bridgers, no sad songs"
python vibe_matcher.py "upbeat songs for a run"
python vibe_matcher.py "clean hip hop, confident and energetic"
python vibe_matcher.py "something sad but also upbeat"   # contradictory -> flagged
python vibe_matcher.py "music"                             # vague -> flagged
```

### Web UI

```bash
python app.py
```

Then open `http://127.0.0.1:5000` in a browser. Type a request into the
text box (exclusions can go right in the same sentence, e.g. "no sad
songs", "clean only") and click **Find songs**.

`app.py` is presentation only — a thin Flask wrapper. All parsing,
validation, and the single AI call still live in `vibe_matcher.py` and are
reused as-is via `get_recommendations()`, so the CLI and the web UI share
exactly one code path for turning a request into a validated result. The
low-confidence banner, the "fewer than 5 results" fallback, and the
per-song reasoning/tags all work identically in both front ends.

The model used for the single AI call defaults to `claude-haiku-4-5-20251001`
(fast and inexpensive — the task is closed-set judgment, not open-ended
generation) and can be overridden with the `VIBE_MATCHER_MODEL` environment
variable.

## Project layout

```
songs.json           the entire universe of recommendable songs (~177 entries)
vibe_matcher.py       core: boring 70% (parsing/validation/formatting) + AI 30% (one Claude call)
app.py                Flask web UI -- presentation only, calls vibe_matcher.get_recommendations()
templates/index.html  web UI page (form + results)
requirements.txt      anthropic, python-dotenv, flask
.env.example          template for your local .env (which is gitignored)
```
